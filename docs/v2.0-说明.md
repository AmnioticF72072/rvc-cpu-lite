# Plus 2.0 — 从「只能翻唱」到「两种生成方式」

v1.x 是一个做得很扎实的**翻唱工具**：给它一段音频，换成目标音色。
v2.0 要解决的问题是：**很多场景下你根本没有那段音频**。

典型情况：想做一段角色配音，但没有现成录音；想给自己的视频配音，
但不想录自己的声音。v1.x 到这里就断了。

所以 2.0 的核心不是加功能按钮，是**换掉「输入」这一层的假设**：

```
v1.x   音频 ──> 变声 ──> 成品
v2.0   音频 ──┐
       文字 ──┴──> 变声 ──> 成品
```

两条路共用同一个模型、同一条管线、同一套质检。区别只在「东西从哪来」。

---

## 一、朗读：文字直接念成你的声音

打一段字，选个情绪，出来的是**你的音色**在念，不是机器人腔。

技术上分三步，每一步都解决一个具体问题：

**1. 文字 → 音节（载体）**

用在线语音合成把文字读成音频。这一步**不需要密钥、不花钱**，
但它只是「载体」——最终听到的音色 100% 来自 RVC 模型，载体只是为了
提供音节、停顿和语调轮廓。

**2. 自动定调（关键，不然声音会闷）**

这是实测出来的一个坑。同一段载体配一个中位 213Hz 的男声模型：

| 移调 | 输出音高 | 质量分 |
|---|---|---|
| +0（照搬翻唱的做法） | 97 Hz | 65 |
| +6 | 127 Hz | 79 |
| **+10** | **136 Hz** | **86** |
| +12 | 166 Hz | 72 |

载体的中位只有 116 Hz，直接转出来是 97 Hz——比目标音域低了一大截，
听感发闷、发虚。所以朗读必须按载体实测音高算一个移调，把它推进模型舒适区。
程序自动做这件事，也可以手动覆盖。

**3. 换音色**

跟翻唱完全一样，走同一条 `RvcPipeline`。

**7 种情绪**：平静 / 温柔 / 欢快 / 激动 / 悲伤 / 严肃 / 耳语。
情绪作用在「念」的语调上（语速、音高、音量三元组），RVC 会保留语调轮廓，
所以情绪能活下来，只是音色被换掉。

> 有个技术限制要说清：Edge TTS 7.x 移除了 SSML 的 style 标签，
> 所以做不到「用撒娇的语气念」这种细粒度风格控制。情绪只能靠
> 语速/音高/音量组合表达——对「载体」来说够用，但别期待戏剧化表演。

## 二、架构：为什么这次要拆

v1.3 结束时 gui.py 有 1454 行，15 个路由。加任何一个功能都要往同一个文件里
塞，改一处得通读全文——这是真会出事的结构。

2.0 按**职责**拆开：

```
app/
  core.py       状态 + 管线生命周期（谁都要用，但不准混业务逻辑）
  reading.py    朗读任务（唯一需要 TTS 的地方）
  __init__.py   对外只暴露这几个名字
gui.py          路由 + 前端（薄入口，双击依然能用）
rvc_cpu/
  tts.py        语音合成封装（载体、情绪、切句）
  read.py       朗读编排（载体 → 定调 → 变声 → 质检）
```

拆分的判据是「**改这个功能时，需要读几个文件**」：
- 改朗读逻辑 → 只碰 `reading.py` + `read.py`
- 改状态字段 → 只碰 `core.py`
- 改界面 → 只碰 `gui.py`

迁移时用的是「保留同名引用」策略：`gui.py` 里 `from app.core import ...`，
原有 15 个路由和任务代码**一行都没改**。所以迁移后回归测试 21/21 直接通过——
零回归不是因为运气，是因为没动被验证过的代码。

## 三、算子级优化：做了、测了、诚实汇报

用户要求「针对各种算子专门优化」。这里把实测过程完整写下来，包括**失败的那部分**。

### 3.1 先定位瓶颈（不猜）

给管线每个阶段打桩计时：

| 阶段 | 3 秒音频 | 10 秒音频 |
|---|---|---|
| **生成器 HiFi-GAN** | 10.30s / **72.6%** | 21.72s / **79.4%** |
| ContentVec 特征 | 1.53s / 10.8% | 2.65s / 9.7% |
| RMVPE 基频 | 0.55s / 3.9% | 1.31s / 4.8% |
| 其他（切块/拼接/IO） | 1.81s / 12.7% | 1.63s / 6.0% |

**结论：生成器占 73~79%。优化 RMVPE 或 ContentVec 都是白费力气。**

### 3.2 图优化级别：有效，保留

原代码用 `ORT_DISABLE_ALL`（注释说为了避开 Where 算子坑）。实测四档：

| 级别 | 推理耗时 | 相对现状 | 加载 |
|---|---|---|---|
| DISABLE_ALL（原状） | 11.55s | — | 2.6s |
| **ENABLE_BASIC** | **10.03s** | **1.15x** | **1.9s** |
| ENABLE_EXTENDED | 10.50s | 1.10x | 2.4s |
| ENABLE_ALL | 10.81s | 1.07x | 2.0s |

`ENABLE_BASIC` 最快，加载还快 27%，且不碰 Where 算子问题（BASIC 只做常量折叠
这类安全优化）。**已改，端到端单句延迟从 23.5s 降到 9.7s。**

### 3.3 线程数：现状已是最优

| 线程 | 推理耗时 |
|---|---|
| 4 | 5.87s |
| **6** | **5.82s** ← 最快 |
| 8 | 7.73s（慢 33%） |
| 12 | 8.56s（慢 47%） |

i5-10400 是 6 核 12 线程，超线程在密集卷积上起了反效果（同步屏障开销）。
现有配置 `intra_threads=6` 正好，**不动**。

### 3.4 INT8 量化：孤立有收益，端到端无效 → 弃用

这是最值得记录的一部分。

**孤立微基准**（只测生成器单算子）看起来很好：

| 配置 | 推理 | 提速 | SNR |
|---|---|---|---|
| FP32 | 10.05s | — | — |
| INT8 MatMul/Gemm | 7.79s | **1.29x** | 38.6 dB |

SNR 38.6 dB，失真几乎不可闻。所以我把它集成进去了（自动检测
`models/quant/*.int8.onnx`，存在就用）。

**但端到端一测就露馅**：

| 配置 | 加载 | 转换（5 秒音频） | RTF |
|---|---|---|---|
| INT8 | 28.0s | 17.83s | 3.57 |
| FP32 | 28.4s | 17.44s | 3.49 |

**0.98x，等于没有。**

原因三条：
1. 生成器只占端到端 73%，提速被反量化（dequantize）开销吃掉
2. 量化模型额外常驻 122 MB；本机 16G 物理内存常年满载，内存带宽才是真瓶颈
3. **i5-10400 是 Comet Lake，没有 AVX-512 VNNI**（Ice Lake 才引入）。
   INT8 只能走 AVX2 模拟路径，理论收益本就有限

所以：**弃用**。模型已移到 `_归档_INT8_实测无收益/`，脚本留在
`tools/quantize_gen.py`，换到支持 VNNI 的机器可以重新评估。

> 教训：孤立微基准会骗人。任何优化都必须端到端测，
> 而且要同一进程交替测（排除系统负载漂移）。

## 四、关于「实时」：做不到，不糊弄

实测纯 CPU 的 RTF（实时倍率，<1 才能实时）：

| 音频长度 | 耗时 | RTF |
|---|---|---|
| 2 秒 | 9.75s | 4.87 |
| 3 秒 | 11.68s | 3.89 |
| 5 秒 | 10.61s | 2.12 |
| 15 秒 | 29.41s | 1.96 |

**RTF 1.96~4.87，物理上做不到麦克风级实时变声。**

能做到的是「按句流水线」：逐句合成、逐句变声，进度按句报。
体感是「写完一段，等几秒出音」，不是「边说边出」。

顺带说明一个硬件事实：CMP 30HX 虽然是 NVIDIA 卡（计算能力 7.5，驱动能识别），
但它是矿卡、无显示输出，且本机没装 CUDA 运行时。走 GPU 需要额外装
onnxruntime-gpu + cudart + cublas（约 700MB），且矿卡的 DX/CUDA 互操作
在无显示设备时不稳定。**这次明确不做**，保持纯 CPU 路线的可复制性。

## 五、关于二次元角色模型：为什么没有内置

用户希望能内置二次元角色音色（动漫/二游）。这里必须讲清一个现实问题：

**RVC 角色模型 = 用某位真人声优的声音训练的。** 打包分发给别人，
涉及声音权与著作权，属于侵权行为。这不是技术问题，是法律问题。

所以 v2.0 的做法是：

1. **不内置任何角色模型**（现有 `myvoice51` 是用户自己的声音，没问题）
2. 把**模型库做成真正的库**：分类、元数据、导入校验都做好，
   用户从合法来源拿到模型后一键导入
3. 在文档里给出**合法来源清单**（见下），并说明各自的授权情况

### 合法来源（自行获取，注意授权）

| 来源 | 说明 | 授权注意 |
|---|---|---|
| **自己的声音** | 用 RVC 训练自己的模型，最安全 | 无风险 |
| **ModelScope 魔搭** | 国内直连快，中文模型多 | 逐个看模型页的许可声明 |
| **voice-models.com** | 全球最大的 RVC 模型库（19 万+），托管在 HuggingFace | 标注 Community 的多为粉丝自制，**商用需谨慎** |
| **HuggingFace** | 搜索 `rvc` + 角色名 | 看仓库的 license 字段 |

**红线**：真人明星、主播、声优的声音模型，未经授权不得商用或公开传播。
粉丝二创模型用于个人娱乐通常没人管，但一旦涉及商业发布就是侵权。

## 六、这一版做了什么、没做什么

### 做了

- 朗读模式（文字 → 你的音色），含 7 种情绪、11 个载体语音
- 朗读自动定调（实测把质量分从 65 提到 86）
- 双模式界面（翻唱/朗读一键切换，各自独立参数区，模式记忆）
- 架构拆分：`app/` 包承载状态与任务编排
- 算子优化：图优化 1.15x（生效），线程数验证（已最优），INT8 实测后弃用
- 回归验证：旧端点 21/21、v1.3 特性全过、队列全过

### 没做（留给 2.1 / 3.0）

- **麦克风实时变声**：RTF 1.96，硬件不够，等更强的 CPU 或 GPU 路线
- **输出格式选择**（flac/mp3）：目前固定 wav
- **多模型融合**：CPU 跑多遍太慢
- **角色模型内置**：法律问题，见上文
- **长文本分章朗读 + 自动配乐**：想法有了，没实现

## 七、怎么用

**翻唱**（和以前一样）：双击 `启动界面(Plus).bat` → 拖音频 → 分析音高 → 开始转换

**朗读**（新）：
1. 双击 `启动界面(Plus).bat`
2. 顶部切到「朗读（文字）」
3. 打字（按句自动切，上限 5000 字）
4. 选情绪（欢快/温柔/悲伤差别很明显）
5. 载体声音留「自动」就行——程序会按模型音域选同性别的
6. 移调留「自动定移调」
7. 点「念出来」

**注意**：朗读的文字转音节那一步要联网（免费、不要密钥）。
断网时这一步会失败，但翻唱功能完全不受影响。
