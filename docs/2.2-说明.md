# Plus 2.2 — 能直接听，能自带分离，能在赛扬上跑

这一版解决三件不同层面的问题：

| 问题 | 层面 | 结论 |
|---|---|---|
| 朗读结果只有文件，没法直接听 | 交互 | 自绘播放器（波形 + 大按钮 + 拖动 + 循环 + 下载） |
| 分离要外部环境，包里跑不了 | 架构 | 内置 torch + demucs 进包，独立后端层 |
| 赛扬双核跑不动 / 慢到以为卡死 | 适配 | 低端 profile + 自动降档 + 明确告知 |

---

## 一、播放器：从"给你个文件"到"直接出声"

### 之前是什么样

朗读完成之后，界面上只有一行文件路径和一个"打开输出文件夹"。

浏览器原生 `<audio controls>` 其实一直在，但它在卡片布局里只渲染成一条细线，
很多人根本认不出那是播放器 —— 等于没有。

### 现在是什么

自绘的一套播放器，两边（翻唱 / 朗读）共用同一个组件：

- **波形图**：不是装饰。能一眼看出"这里确实有声音、哪里是静音"，
  比单纯进度条有用得多。已播放部分染成蓝色。
- **大播放键**：52px 圆形按钮，播放中变成绿色暂停图标。
- **点波形跳转**：想听某一句，直接点那个位置。
- **时间显示** / **音量** / **循环** / **下载**。
- 朗读完成会**自动开始播放** —— 点完"念出来"就该听到声音。

### 过程中挖出来的两个真 bug

**bug 1：播放位置被反复清零**

界面每秒轮询一次状态。第一次实现里，每次轮询都重新把音频塞进 `<audio>`，
于是播放位置被重置 —— 表现为"放两秒自己回到开头，根本没法听"。

修法：给音频内容算一个指纹（用输出路径，不用带时间戳的 URL），
同一份内容只装载一次。

**顺手踩到的坑**：去重分支里我一开始写了"如果暂停就自动 play()"。
但**播完之后 `paused` 也是 true**，于是每秒都被重新播放一次 —— 变成无限循环。
这个错误只有真跑起来才会暴露，静态审查看不出来。

**bug 2：服务器不支持 Range，导致根本不能拖动进度**

这个是更根本的问题。浏览器的媒体元素靠 **HTTP Range 请求**做 seek：
服务器不认 `Range` 头时，`audio.seekable` 是空的，给 `currentTime` 赋值
**会被静默忽略** —— 不报错，就是不生效。

实测证据：波形点击算出的比例是 `0.600`（完全正确），但播放位置纹丝不动。

修法：`/api/audio` 改为支持 `Range`，返回 `206 Partial Content` +
`Accept-Ranges: bytes` + `Content-Range`。改完之后：

```
seekable: 2.2            ← 之前是"空(不能跳转)"
点 60% 处跳转到: 1.32 秒 (应≈1.32)  OK
```

### 怎么验证的

没有靠"看起来对"。写了个 CDP（Chrome DevTools Protocol）客户端，
起真实 headless 浏览器，用**真实鼠标事件**点击波形，读回播放器内部状态：

```
makePlayer 存在: True
audio.duration: 2.20 秒
波形不透明像素: 4540 / 28560  → 波形已绘制: True
播放中: True   当前时间: 1.64 秒   按钮变'播放中': True
seekable: 2.2
点60%处跳转到: 1.32 秒 (应≈1.32)  OK
循环已开: True   音量设 50%: 0.50
```

> 这里有个教训：第一版测试用 `new MouseEvent()` 合成点击，`offsetX` 恒为 0，
> 测出来的结果是假失败。必须用 CDP 的 `Input.dispatchMouseEvent` 发真实事件。

## 二、内置分离：从"要外部环境"到"开箱即用"

### 之前是什么样

分离（去掉伴奏 / 剥掉和声）依赖 torch。而打包版的 runtime 里**没有 torch**
（torch 有几 GB，为了体积一直没内置）。所以：

- 分离功能在整合包里实际上是**不可用**的
- 报错只说"没有分离后端"，用户不知道该装什么
- 就算用户机器上有 torch，路径也是硬编码的，换台机器就找不到

### 现在的架构

拆成独立的后端层，职责分明：

```
rvc_cpu/sep/
  __init__.py   能力探测 + 对外说明（能用什么、缺什么）
  worker.py     选解释器、准备环境变量（内置 torch / 外部 Python 兜底）
  karaoke.py    找 UVR 去和声模型
rvc_cpu/separate.py   调度：起子进程、解析进度、错误翻译
tools/sep_worker.py   子进程里的实际执行
```

内置内容：

| 组件 | 体积 | 说明 |
|---|---|---|
| torch (CPU 版) | ~600 MB | 不装 CUDA，用不上 |
| demucs | 少量 | 分人声 / 伴奏 |
| htdemucs 权重 | 80 MB | 预置，离线可用，不用首次联网下载 |

### 为什么跑在子进程里

三条理由，都是踩出来的：

1. torch 光 import 就几百 MB 常驻内存。本机 16G 常年吃紧，
   主进程装下它之后跑推理必然掉进换页。
2. 分离是分钟级任务，放主进程会把界面一起卡住（HTTP 无法响应）。
3. torch 崩了只带走子进程，界面还在，用户能看到报错并重试。

### 依赖是怎么补齐的

demucs 4.1 的依赖链比想象的深。逐个撞出来补上的：

`sphn` → `tqdm` → `torch` → `julius` → `einops` → `openunmix` →
`lameenc` → `treetable` → `dora-search` → `omegaconf` → `hydra-core`

> 教训：`pip install demucs --no-deps` 之后必须真的 `import demucs.api`
> 验证一遍，光看文件在不在没用 —— 它 import 链上一层一层往下拉，
> 缺一个就报一个，得跑到不再报错为止。

> 另一个坑：补依赖时**不能直接 `pip install julius`**（它依赖 torch）。
> pip 不认识包里已有的 torch，会去 PyPI 重新下一份 **CUDA 版**（2.5GB 起）。
> 我因此白等了 15 分钟，最后必须全部加 `--no-deps` 逐个补。

### 实测结果（8 秒合成素材，i5-10400 6 线程）

| 指标 | 数值 |
|---|---|
| 分离耗时 | **35.5 秒**（overlap 0.5） |
| 人声轨 60Hz 能量占比 | **0.0000**（原混音 0.2750 → 贝斯完全剥离） |
| 伴奏轨 60Hz 能量占比 | **0.9766**（贝斯完整保留） |
| 伴奏轨 200~300Hz（人声区） | **0.0002**（人声基本清空） |
| 长度对齐 | 8.00 秒 → 8.00 秒，差 0.000 秒 |

overlap 的速度代价（同一段素材）：

| overlap | 耗时 | 取舍 |
|---|---|---|
| 0.25 | 27.7 秒 | 最快，交界处可能有点串音 |
| **0.50** | **33.3 秒** | **默认值，折中** |
| 0.75 | 52.4 秒 | 质量收益抵不上多花一倍时间 |

### 还有两个只在实际运行中才暴露的 bug

**bug 1：sphn 读不了中文路径。**
demucs 的 `separate_audio_file()` 内部走 sphn（Rust 实现），在本程序的安装目录
「声音转换Plus」上直接报 `When trying to load using sphn`。
改用 soundfile 自己读音频 → 转成 tensor → 调 `separate_tensor()`，绕开它。

**bug 2：起子进程时把 PYTHONPATH 清了。**
原来用 `python -m demucs` 起子进程，为防止沙箱注入的 sitecustomize shim，
代码里把 PYTHONPATH 删掉了 —— 但这样一来子进程就找不到包内的
`runtime\_sep_libs`，报 `No module named demucs`，**被上层误判成"没有分离后端"**。
现在直接在本进程调 API，不重复起进程，也不再有环境变量问题。

## 三、赛扬双核适配

这台机器不是"慢一点"，是**慢一个数量级**，而且内存和缓存都小。
默认配置（6 线程、overlap 0.75）在双核上会跑到几十分钟甚至 OOM。

### 修掉的第一件事：核心数被算错

原来的推断逻辑是「物理核 = 逻辑核 ÷ 2」。

但**赛扬大多是 2 核 2 线程，没有超线程**。于是：

```
logical = 2  →  physical = 2 ÷ 2 = 1  →  线程数 = 1
```

**白白浪费掉一半算力，速度直接砍半。**

现在对赛扬 / 奔腾 / Atom 单独判断，按型号取真实核数，2 核机器就用 2 线程。

### 新增 lowend-2core profile

| 参数 | 通用 CPU | lowend-2core | 理由 |
|---|---|---|---|
| intra_threads | 物理核数（6） | `min(逻辑核, 2)` | 双核机器不能超配，超了只会互相抢 |
| inter_threads | 1 | 1 | 同上 |
| 分离 overlap | 0.75 | **0.30** | 0.75 在双核上要一个多小时，降到 0.30 是"能用"和"不可用"的差别 |

### AVX2 风险检测（这个比速度更要紧）

onnxruntime 官方构建**要求 AVX2**。

Atom 血统的赛扬（N4000 / N4020 / N4120 / N5100 / J4125 这类）
**只有 SSE4.2，没有 AVX / AVX2**。在这些机器上会直接崩在
`Illegal instruction` 或 DLL 加载失败，而且**报错完全看不出是 CPU 不支持**。

所以加了风险分级：

| 型号 | 等级 | 提示 |
|---|---|---|
| N/J 系列、Atom | **high** | 明确告知"很可能跑不起来" |
| 其他赛扬 / 奔腾 | warn | 提醒"若崩溃可能是缺 AVX2" |
| 酷睿 i3/i5/i7 | 无 | 不打扰 |

界面上的机器提示条会同时显示：CPU 型号、实际用几线程、预期速度。
**不提示的话，用户会以为程序卡死了。**

### 手动强制开关

有些 OEM 机器的 CPU 型号字符串很怪，自动判断会漏。所以留了一个开关：

```
set RVC_LOWEND=1     →  强制按低端处理
set RVC_LOWEND=0     →  强制按普通机器处理
```

写进 `启动界面(Plus).bat` 也行。

### 验证方式

用 monkeypatch 替换 CPU 型号，把典型型号跑了一遍，检查识别、线程数、
AVX2 等级是否正确，**同时确认 6 核 i5 不会被误判**（避免误伤正常机器）：

| 型号 | 逻辑核 | 识别低端 | AVX2 | 线程数 |
|---|---|---|---|---|
| Celeron G5905 | 2 | 是 | warn | 2 |
| Celeron N4020 | 2 | 是 | high | 2 |
| Celeron N5105 | 4 | 是 | high | 2 |
| Celeron J4125 | 4 | 是 | high | 2 |
| Pentium Gold G6400 | 4 | 是 | warn | 2 |
| Atom x5-Z8350 | 4 | 是 | high | 2 |
| **Core i5-10400** | 12 | **否** | 无 | 6 |
| **Core i5-12400** | 12 | **否** | 无 | 6 |

全部通过。

### 赛扬用户的预期

这台机器上 4 分钟的歌大概要 **15~25 分钟**。界面会直接把这个数字说出来，
而不是让人对着进度条猜。

如果嫌慢，唯一有效的手段是换机器 —— 这套流程是纯 CPU 计算密集型的，
能省的（线程、overlap）已经省到底了。

## 五、没做的

- **分离用 GPU**：本机显卡是矿卡且无 CUDA 运行时，不做。
- **更低端的 x86（无 AVX2）**：需要重编 onnxruntime 才能支持，
  且速度会慢到没有实用价值，不做。
- **播放器倍速**：加了也没多少人用，先留白。
