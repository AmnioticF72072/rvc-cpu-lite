# Plus 2.2.3 —— 修复"音高整体偏低五个半音"

这一版修掉的是**最要命的一个 bug**：从 0.x 到 2.2.2，所有人声转换出来都比原唱**低 5 个半音左右**。

不是风格问题，是算错了。

---

## 现象

用过的人都遇到过，但很难描述成"低五度"：

- 转出来"不像本人"，音色对但人不对
- 听着发闷、发"电"、像是合成器
- 有些歌整首跑调，但又不是每个音都错
- 调 `--key` 能勉强找回一点，可总是差半口气

现在回头看，这些描述全都指向同一件事：**模型拿到的音高曲线是错的**。

---

## 原因：Mel 频率刻度用错了

RMVPE（音高提取模型）不是直接听波形的，它先算 128 维 Mel 频谱再送进网络。
Mel 滤波器组的**频率刻度**有两个流派：

| 刻度 | 公式 | 谁在用 |
|---|---|---|
| **HTK** | `m = 2595 · log10(1 + f/700)` | 语音识别、**RMVPE 训练时用的就是这个** |
| slaney | 1000Hz 以下线性、以上对数 | librosa 的默认值（`htk=False`） |

我们的 `mel.py` 当初是照着 librosa 的**默认参数**写的，也就是 slaney。
librosa 自己没写错，错的是"默认值恰好不是 RMVPE 要的那个"。

刻度一错，同一个频率就落到不同的通道号上。网络看到的是"错位的频谱"，
输出自然是一串错的 cents（音分），最后由 `f0 = 10 · 2^(cents/1200)` 换算成 Hz 时，
整条曲线被系统性地拉低。

**关键是这个错误不会报错**。它不崩、不警告、不NaN，就是安静地给出错的音高。
所以它能活过 2.0、2.1、2.2 三个大版本。

### 实测偏差

用 5 个精确已知频率的合成音测（16kHz，加二次谐波）：

| 真值 | 旧版（slaney）读数 | 偏差 |
|---|---|---|
| 196.00 Hz | 140.64 Hz | **−575 音分** |
| 294.00 Hz | 209.32 Hz | **−588 音分** |
| 392.00 Hz | 286.18 Hz | **−545 音分** |
| 523.25 Hz | 399.57 Hz | **−467 音分** |

修好之后：

| 真值 | 新版（HTK）读数 | 偏差 |
|---|---|---|
| 110.00 Hz | 109.86 Hz | −2.2 音分 |
| 196.00 Hz | 196.29 Hz | +2.6 音分 |
| 294.00 Hz | 294.50 Hz | +2.9 音分 |
| 392.00 Hz | 392.43 Hz | +1.9 音分 |
| 523.25 Hz | 523.67 Hz | +1.4 音分 |
| 659.25 Hz | 659.23 Hz | −0.1 音分 |

滤波器组本身与 `librosa.filters.mel(htk=True)` 逐元素完全一致（`max|diff| = 0`）。

### 对成品的实际影响

同一段 15 秒人声（中位 187.6 Hz），同一套参数，只改刻度：

| | 输出中位音高 | 与输入的音高差 |
|---|---|---|
| 输入原声 | 187.6 Hz | — |
| **修复后** | **187.6 Hz** | **+9.8 音分** |
| 旧版 | 140.7 Hz | **−543 音分** |

低 543 音分 ≈ **5.4 个半音**。也就是说旧版把每首歌都当成"低了五度的人"来唱，
模型只能硬撑——这正是"紧、虚、发闷、带电"的来源。

## 顺便修的四个

### 1. 分块步长写死成 1024 帧

`convert_file` 里算每块最多走多远时用的是模块常量 `GEN_T = 1024`，
而不是这个模型**实际**的定长帧数 `self.gen_T`。

导入一个按 `--T 512` 导出的模型时，块会超出生成器容量 → 超出部分被截断 →
**输出比输入短、一整段错位**（听着像跳词、漏句）。现在按 `self.gen_T` 算，
并且真的发生截断时会打印警告，不再静默出坏音频。

### 2. 界面显示的设备是假的

`[设备] CUDA(GPU)` 曾经是一句谎话。

onnxruntime 在加速后端加载失败时**不会抛异常**——它打一条日志，然后用 CPU 跑完。
原代码直接 `return session`，于是标签一路显示 CUDA，实际 RTF 是 CPU 的。
用户只会觉得"勾了 GPU 还是这么慢"，根本查不到原因。

现在建完 session 会核对它**实际**注册了哪些 provider，对不上就退回 CPU 并明确报告：

```
[设备] CUDA(GPU)
[警告] CUDA(GPU) 加载失败，退回 CPU: 加速后端 CUDAExecutionProvider 没能真正加载
[设备] 实际使用：CPU（加速后端加载失败，已退回） —— 功能不受影响，只是慢一些
```

### 3. 混音重采样没有抗混叠

人声轨 48k、伴奏轨 44.1k 是常见组合。原来的 `_resample` 是纯线性插值，
降采样时 22kHz 以上的能量会**折叠回可听频段**，听起来是"沙"、是"电"。
现在走 soxr 的 VHQ 档（本来就是项目依赖）。

### 4. 命令行默认只认 `myvoice51.onnx`

导入自己的模型（比如「姬子.onnx」）后再跑 `convert.py`，不带 `-m` 会直接报
"缺模型文件"——模型明明就在 models 目录里。现在默认读模型库中**当前激活**的那个。

## 你该怎么办

**重新转一遍。** 之前所有用本工具转出来的成品，音高都是低的，素材本身没救，
只能重跑。这一版不需要改任何参数——以前为了"救回来"而加的 `--key` 偏移，
现在应该归零（或者按正常听感重定）。

命令行和老界面都不用改用法。模型、索引、配置文件完全兼容。

---

## 验证方式

1. **合成音对拍**：5 个已知频率，误差 ≤3 音分（上表）
2. **librosa 对拍**：滤波器组 `max|diff| = 0.000e+00`（HTK / slaney 两档都比了）
3. **端到端**：15.0 秒进 → 15.00 秒出，输出中位音高与输入一致
4. **旧版对照**：同素材同参数，旧刻度输出低 543 音分

## 一句反省

这个 bug 之所以活得久，是因为它**只影响听感，不影响任何指标**。

以前排查"带电"，量的是频谱形状、分离残留、谐波外能量——全都正常，
因为波形确实是干净的，错的只是条件。含"音高"的指标又都在用同一个错的 f0 去量，
自己跟自己比当然自洽。

教训：**凡是"把某个模型的前端重新实现一遍"的地方，都要跟原实现逐元素对拍**，
不能只对拍"看起来差不多"。这次的对拍基准是 `librosa.filters.mel(htk=True)`。
